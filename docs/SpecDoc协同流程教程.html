系统概述

什么是 Spec Doc 协同工程？

将产品需求、功能设计、测试用例、项目概览和知识沉淀五大环节串联成标准化工作流，确保文档与代码同仓管理、版本同步、团队协同。

📋 标准化

统一的目录结构、文档模板和提交规范

🔗 可追溯

Git 历史追踪每次文档变更，PRD→设计→测试全链路关联

🤝 团队协同

产品经理、开发组、测试组、项目经理各司其职

☁️ 远程同步

本地文档通过两阶段同步推送至远程文档中心仓库

🧠 知识沉淀

每个开发周期的经验自动归档为团队知识库

📊 进度透明

自动化进度收集与钉钉播报，消除信息孤岛

初始化检查清单

阶段 2 / 6

PRD 文档产出

PRD 必须包含以下章节，任何一项缺失都必须补充：

  • 需求背景
  • 目标与范围
  • 功能需求（函数级颗粒度）
  • 非功能需求
  • 验收标准
  • 交付计划
  • 术语定义
  • 原型/设计

1

5
开发实施（按 TDD 原则：失败→实现→通过→重构） 开发组
6

7
/document-compound 生成 功能级 "用户登录" → 上传 全员

关键原则

理性化防护

以下常见借口会导致技术债，必须严格防护：

❌ "手动建文件夹就行"

✅ 必须初始化：只有初始化才能保证目录标准化和 git commit 闭环

❌ "先开发后补文档"

✅ 强制前置：没有设计文档不能开始开发

❌ "测试后面补"

✅ 强制前置：测试必须先行，不能后补

❌ "进度差不多就行"

✅ 强制精确：进度必须精确到百分比

❌ "项目结束不用总结"

✅ 强制总结：不总结就是知识浪费

❌ "需求不明确先写个大概"

✅ 强制澄清：使用 /brainstorming 或基础澄清模板
